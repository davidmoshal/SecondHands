Movement Tracker Architecture

A camera-based fitness tracker on the Snapdragon X Elite laptop. Pose estimation runs through ExecuTorch, rep counting is deterministic, and a small trained classifier is the NPU showcase. The Wiki page Wiki/design/tech-stack.md is the source of truth; this page is the walkthrough.

1 · Data flow

From camera frame to rep count

Every layer talks to the next through one kind of data. Keypoints are the hinge: everything above them is model work, everything below them is ordinary application code.

2 · Processes on the laptop

Why the NPU needs a second process

Windows 11 ARM64 has native wheels for PyTorch, MediaPipe and ONNX Runtime, but not for ExecuTorch or OpenCV. So the day-one service runs as x64 Python under emulation, where every package exists. The Qualcomm NPU is reachable only from a native ARM64 process with the QNN libraries, so that part is a separate runner the service talks to over a local socket.

Rep counting and form cues need no training at all. Quantization needs about 100 calibration frames of people exercising at the demo distance; record them on day one.

4 · Conversion handoff

What to give the Qualcomm engineer, and what to ask back

Give

  1. PyTorch nn.Module plus weights that load without MMPose training code (for RTMPose, the qai_hub_models wrapper).
  2. Input contract: shape, float32 RGB, normalization, how the person crop is made.
  3. Target: QcomChipset.SC8380XP, ExecuTorch 1.5.1, QAIRT 2.37.0, Windows 11 ARM64, export under x64 Python.
  4. About 100 calibration frames and 10 saved PyTorch reference outputs (.npy).
  5. Precision preference: 8a8w first, 16a8w if keypoint error grows.
  6. The starting recipe experiments/qnn_export_pose.py (untested, written from the backend docs).

Ask back

  1. The .pte with the exact export command and tool versions.
  2. The native ARM64 runner or backend DLL build, or confirmation the hackathon bundle runs it.
  3. A profiler or ETDump trace showing operators on the HTP, plus warmed latency.
  4. The list of operators that fell back to CPU.
  5. Measured keypoint error against the reference outputs per precision.

Core of the recipe

quantizer = QnnQuantizer()                      # 8a8w default
m = torch.export.export(model, (x,), strict=True).module()
m = prepare_pt2e(m, quantizer); [m(c) for c in calib]
q = convert_pt2e(m)
spec = generate_qnn_executorch_compiler_spec(
    soc_model=QcomChipset.SC8380XP,
    backend_options=generate_htp_compiler_spec(use_fp16=False))
pte = to_edge_transform_and_lower_to_qnn(q, (x,), spec).to_executorch()
5 · Interface contract

Three messages the frontend builds against

pose · every frame

 "inference_ms":38.2,
 "runtime":"executorch-xnnpack",

 "keypoints":[[0.51,0.22,0.98], …17],

           "trunk_lean":12.0}}

rep_event · per repetition

 "session_id":"s-20261017-01",
 "exercise":"squat","rep":7,
 "phase":"up","duration_ms":2150,
 "depth_score":0.82,
 "cues":["Go a little deeper"],
 "source":"rules"}

session_summary · at stop

{"type":"session_summary",
 "session_id":"s-20261017-01",
 "exercise":"squat","reps":12,
 "median_rep_ms":2200,
 "form_score":0.78,
 "baseline":{"reps":8,
   "form_score":0.70}}

Keypoints are normalized to the image with a confidence per point. source says whether the rule counter or the classifier produced the event, so both can be shown during evaluation.

6 · Order of work

Two days, one rule: the demo never waits on a conversion

Day 1

  • Pick the camera with one capture test each on the Dell.
  • Install x64 Python 3.12 and run just smoke-yolo-pose-executorch on the laptop; measure fps.
  • Angles, squat and push-up state machines, the three messages, SQLite.
  • Record calibration frames and a small labeled clip set; hand RTMPose to the Qualcomm engineer.
  • Session screen with skeleton overlay and rep counter against real messages.

Day 2

  • Train and export the window classifier; compare with the rule counter on held-out clips.
  • If the QNN .pte loads, swap the pose backend and capture the profiler trace; otherwise keep CPU and say so.
  • Progress screen, baseline comparison, stop and restart checks.
  • Freeze artifacts; measure warmed latency, memory and sustained behavior.
  • Presentation mapped to the judging weights: use case 40, technical 25, on-device efficiency 15, docs 10, demo 10.
Sources and evidence live in the repository Wiki: design/tech-stack.md, references/models/pose-candidates.md, experiments-before-saturday.md. AI Hub latency figures are Qualcomm's published numbers; only the YOLO CPU export has been run by the team.
